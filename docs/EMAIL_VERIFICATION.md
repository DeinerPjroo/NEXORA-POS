# Verificación de correo · 0.30

La cuenta muestra email_verified_at y el estado real en Seguridad personal. GET auth/email-verification devuelve verified y delivery_available. POST solicita únicamente el correo propio; rechaza email/user_id/tenant_id enviados por cliente. Tres solicitudes por minuto por cuenta. No se agrega un bloqueo general de empresas existentes sin correo verificado mientras SMTP externo sigue pendiente.

Reutiliza MustVerifyEmail, VerifyEmail y EmailVerificationRequest de Laravel13. La notificación en español dirige a /verificar-correo con una ruta relativa firmada que vence en60 minutos. El cliente solo admite el patrón concreto del endpoint y conserva el enlace al pasar por login; no acepta destinos externos. El usuario confirma mediante POST con cookies/CSRF a auth/email/verify/{id}/{hash}; signed:relative valida firma y vencimiento antes de confirmar, con diez intentos/minuto por cuenta. No tomar identidad ni valores firmados del body. No se verifica un correo al abrir un GET o por una bandera del navegador.

El id/hash debe coincidir con el usuario autenticado. Dentro de transacción Tenant→User se comprueba otra vez el correo vigente, se marca email_verified_at y se registra auth.email_verified. Un fallo de auditoría revierte el estado; repetir un enlace vigente de la misma cuenta ya verificada no duplica auditoría ni cambia permisos. Una sesión bloqueada devuelve423 para solicitud y confirmación; invitados no tienen acceso. No se guarda ni registra la URL firmada en auditoría.

log/array no son servicios de envío. Failover/roundrobin que incluyan un destino local o una configuración circular se consideran indisponibles. En ese caso no se genera notificación y la API devuelve503; la interfaz muestra el motivo y deshabilita solicitar. Un transporte externo configurado puede intentarlo: respuesta202 solo después de aceptar el transporte, sin garantizar llegada a bandeja. Errores son genéricos y el log solo incluye clase de excepción. Configurar MAIL_MAILER/MAIL_HOST/MAIL_PORT y credenciales localmente; no versionarlas. El envío SMTP y llegada externa siguen pendientes de prueba real.

Pruebas nativas cubren el contrato firmado real, notificación interceptada, confirmación válida/idempotente, firma alterada/ausente/vencida, cuenta/empresa ajenas, correo cambiado entre lecturas, CSRF, bloqueo, límites, fallos de transporte y rollback. Chromium comprueba estados/ausencia de envío local, regreso desde login y rechazo real de firma inválida/destino externo. El fixture CLI exclusivamente e2e.sqlite permite preparar una cuenta ya verificada para comprobar su presentación; no sustituye la confirmación nativa ni prueba recepción SMTP. No hay endpoint de bypass ni nueva migración/dependencia.

Referencia: [Laravel13, Email Verification](https://laravel.com/framework/docs/13.x/verification). El flujo SPA adapta la confirmación a POST y firma relativa para conservar CSRF y los puertos existentes.
